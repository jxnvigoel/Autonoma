# ADR-001: System Architecture Style — Modular Monolith

## Status
Accepted

## Context
The application (SiteAudit Pro) is an offline-first desktop tool designed for local inspection and compliance logging [NFR-04]. The target scale is tier T0 (< 10,000 DAU, ~3,000 local records) with 100% local persistence and zero external cloud dependency [NFR-02]. We must choose between a Modular Monolith and a Distributed Microservices architecture.

## Options Considered
1. **Modular Monolith (Chosen)**: Single deployable desktop application with well-defined internal domain module boundaries (Inspections, Deficiency Indexing, Punch-list Exporter).
   - *Pros*: Zero network hop latency; trivial atomic transactions; zero container/Kubernetes orchestration overhead; 100% offline reliability; fits within budget and 7-week timeline.
   - *Cons*: Horizontal scaling across multiple machines requires future refactoring if multi-user cloud sync is added in v2.
2. **Microservices Architecture**: Multiple distributed services communicating via HTTP/gRPC with container orchestration.
   - *Pros*: Independent service deployment and scaling.
   - *Cons*: Severe violation of Handbook Section 7.2.6 (Must Not over-engineer); introduces network latency, distributed data consistency failures, complex IPC, and heavy memory footprint unsuitable for offline field laptops.

## Decision
Adopt a **Modular Monolith** architecture pattern. The system runs as a unified desktop process with clear internal domain separation.

## Consequences
- Single-process execution guarantees instant in-memory operations and direct embedded database transactions.
- Zero network failures or IPC serialization overhead during offline field inspections.
- Development fits comfortably within the target delivery timeline and budget [G-01].
